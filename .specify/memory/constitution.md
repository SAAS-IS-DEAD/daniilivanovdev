# daniilivanovdev Constitution

## Core Principles

### I. Проверяемые требования и ограниченный объём

Каждая функция MUST иметь пользовательский сценарий и проверяемые критерии приёмки
в спецификации. Обязательные требования тестового MUST быть отделены от согласованных
расширений: публичного фронтенда и синхронизации резюме hh.ru.
Неизвестные требования MUST быть явно отмечены; обрезанный исходный текст нельзя
восстанавливать догадками и выдавать за требования заказчика.
Новые функции и инфраструктура MUST иметь основание в согласованном объёме работы.
Качество решения оценивается по корректности и понятности, а не по количеству кода.

### II. Разделение ответственности без лишних абстракций

GraphQL-слой MUST отвечать за контракт API и передачу управления прикладному слою.
Прикладные сервисы MUST содержать правила приложения; работа с Prisma и базой MUST
быть отделена от GraphQL и пользовательского интерфейса.
Frontend MUST обращаться к backend через API, без прямого доступа к базе.
Модели хранения и API MUST иметь явные границы, чтобы внутренние поля
не становились публичными автоматически.
Каждый дополнительный слой, общий интерфейс или инфраструктурный компонент MUST
решать конкретную задачу, описанную в техническом плане или README.
Микросервисы и универсальные CRUD-абстракции не вводятся без такого основания.

### III. Защита изменений и предсказуемые данные

Публичный API предоставляет только чтение. Воркер пишет в БД через прикладной слой.
При появлении защищённых операций backend MUST проверять авторизацию независимо от UI.
Входные данные MUST проходить серверную валидацию; обязательность полей, ограничения,
порядок выдачи и поведение при отсутствии записи MUST быть определены в контракте.
Если пароли появятся в согласованном объёме, они MUST храниться только в виде стойких хешей.
Секреты и рабочие учётные данные MUST передаваться через конфигурацию окружения,
не попадать в Git, клиентский код, ответы API или логи.
Если авторизация сайта вернётся в согласованный объём, её механизм MUST предусматривать завершение и истечение сессии,
ограничение попыток входа и защиту, соответствующую способу передачи учётных данных.
При использовании cookie MUST быть предусмотрена защита от CSRF.
Публичный API MUST возвращать только предназначенные для публикации данные.
Операции, требующие атомарного изменения нескольких записей, MUST быть атомарными.
Ошибки API MUST быть понятными клиенту и не раскрывать детали базы или стеки.

### IV. Воспроизводимый запуск и доступная проверка

Чистый checkout MUST запускаться по документированной последовательности команд
с использованием Docker. Версии зависимостей MUST фиксироваться lock-файлом.
Схема базы MUST создаваться версионируемыми миграциями, данные визитки — seed-процедурой.
Повторное заполнение MUST не создавать дубликаты; правила обновления существующих
данных, локальных дополнений и результатов синхронизации MUST быть явно описаны.
Первый запуск MUST проверяться на пустой базе; недостающая обязательная конфигурация
MUST приводить к понятной диагностике.
Apollo Sandbox MUST быть доступен проверяющему на развёрнутом приложении и позволять
выполнить пример публичного запроса. Это не отменяет защиту операций изменения.
README MUST содержать запуск, миграции, seed, переменные окружения без секретов,
проверки, примеры запросов и обоснование архитектуры.

### V. Проверка поведения и понятность реализации

Завершённое изменение MUST проходить относящиеся к нему проверки типов, линтер,
сборку и тесты. Проверки MUST подтверждать наблюдаемое поведение, а не повторять
внутреннее устройство функций.
Интеграционные проверки MUST охватывать профиль со связанными данными, атомарность
и идемпотентность синхронизации, ошибочные входные данные и сохранение последней
успешной версии при отказе источника. Публичный API не предоставляет операции записи.
Каждая новая или изменяемая фича MUST иметь unit-тесты поведения; для frontend это
включает компонентные проверки. Каждая backend-фича дополнительно MUST иметь
интеграционные проверки Nest/HTTP/GraphQL с настоящей отдельной PostgreSQL.
До реализации сценария MUST быть проверен ожидаемый падающий тест; после — зелёный
результат. Багфикс MUST включать регрессионную проверку. Фича без этих тестов
не считается выполненной. `npm run verify` обязателен перед завершением работы.
Coverage thresholds нельзя снижать, а продуктовый код исключать ради зелёного CI.
Процент покрытия не является самоцелью или заменой проверки сценариев. UI MUST показывать загрузку, пустые состояния, ошибки и результат
сохранения; разрушительные действия MUST иметь защиту от случайного выполнения.
Запросы связанных данных MUST проверяться на отсутствие роста числа обращений
к базе пропорционально числу возвращаемых элементов из-за отдельных запросов на каждый элемент.
Решения и команды MUST быть объяснены так, чтобы автор мог воспроизвести их и защитить
на разборе тестового; незнакомые GraphQL-понятия объясняются по мере появления.

## Ограничения проекта

- Обязательный стек: Git, TypeScript, Node.js, NestJS, Prisma, GraphQL и Docker.
  Apollo Sandbox является обязательным интерфейсом проверки API.
- Основной продукт — цифровая визитка одного специалиста. Согласованные расширения:
  публичный frontend и отдельный воркер синхронизации резюме hh.ru.
  Авторизация сайта, админка и CRUD отменены по указанию владельца 2026-11-04.
- Рабочая граница: один публичный профиль; запись через seed и согласованную синхронизацию.
  Регистрация, админка, CRUD и серверные сессии не входят в текущий объём.
- PostgreSQL, React/Vite и apps/api + apps/web приняты в техническом плане.
  Воркер hh.ru находится на паузе по указанию владельца.
- Контент MUST основываться на предоставленных автором данных. Придуманный опыт,
  работодатели и достижения не могут публиковаться от его имени; временные данные
  MUST быть явно обозначены как демонстрационные.
- Пользователь подтвердил, что присланный текст является всем доступным тестовым.
  Отсутствующие фрагменты не восстанавливаются догадками и не блокируют планирование.
  Новые требования учитываются только при их явном появлении.

## Процесс разработки и критерии готовности

Работа ведётся через Spec Kit: принципы → спецификация → уточнения → технический план
→ задачи → анализ согласованности → реализация → сверка результата с требованиями.
Конституция задаёт общие правила; spec.md описывает поведение, plan.md — технические решения,
tasks.md — порядок работ. Изменение требований MUST отражаться в затронутых документах.

Публичная визитка реализована. При изменении объёма сначала обновляются требования
и задачи; доступность внешнего источника подтверждается до реального импорта.
Работа выполняется небольшими проверяемыми этапами; Git-коммиты MUST иметь осмысленные
сообщения и не содержать секретов, установленных зависимостей или локальных кэшей.

Перед сдачей MUST быть проверены запуск с пустой базой, публичный GraphQL-запрос через
Sandbox, публичный сайт, синхронизация и сохранность данных при ошибках источника
и после перезапуска. В README MUST быть ссылки на развёрнутое приложение и исходники,
а также описан способ проверки воркера без публикации учётных данных hh.ru.
Отчёт о готовности MUST перечислять выполненные проверки и известные ограничения;
непроверенное поведение нельзя обозначать как проверенное.

## Governance

Эта конституция применяется при составлении спецификации, технического плана,
задач и проверке реализации. Прямые указания пользователя имеют приоритет;
при изменении договорённостей затронутые положения MUST быть приведены в соответствие.

Поправка MUST содержать причину, изменение версии и дату, а также оценку влияния
на спецификацию, план, задачи и существующий код. Отклонение от принципа MUST быть
объяснено конкретным ограничением и отражено в плане; скрытые исключения недопустимы.
Шаблоны Spec Kit не изменяются только ради копирования принципов: они читают этот документ.

Версия следует SemVer: MAJOR — несовместимая отмена или переопределение принципов;
MINOR — новые принципы или существенное расширение правил; PATCH — уточнения без изменения
обязательств. Версия 1.0.0 является первым заполненным вариантом конституции проекта.
