# Нагрузка на публичный GraphQL API

Нужны Node из `.node-version`, `npm ci` и отдельный бинарник **k6 >= 0.57**
(на macOS: `brew install k6`). TypeScript выполняется k6 напрямую; `tsc`
проверяет типы через `npm run typecheck`.

Тест выполняет тот же `GetProfile`, что и сайт: профиль со всеми ссылками,
навыками, опытом и проектами. Запрос читается из frontend `.graphql`, поэтому
изменения запроса автоматически попадают в нагрузочный тест. Тесты только читают данные.
Нужен работающий API с заполненным профилем. По умолчанию цель — `http://localhost:3000`.

```sh
# 5 последовательных запросов и предварительная проверка профиля
npm run test:load:smoke

# 30 секунд разгона, 2 минуты при 20 запросах/сек, 30 секунд спада
npm run test:load

# Ступени 20 → 40 → 80 запросов/сек; всего 5 минут
npm run test:load:stress

# Другая среда и интенсивность (одна итерация = один GraphQL-запрос)
BASE_URL=http://localhost:3000 RATE=50 npm run test:load

# Подробный JSON-вывод в существующую папку artifacts
k6 run -e MODE=load --out json=artifacts/k6.json load/profile.ts
```

`BASE_URL` — origin без пути и завершающего `/graphql`. Для удалённого стенда
задавайте его явно. Не запускайте stress против общего production без согласованного окна.

| Переменная          | По умолчанию            | Значение                                                  |
| ------------------- | ----------------------- | --------------------------------------------------------- |
| `MODE`              | `smoke`                 | `smoke`, `load`, `stress` (npm-команды задают режим явно) |
| `BASE_URL`          | `http://localhost:3000` | Origin API                                                |
| `RATE`              | `20`                    | Запросов/сек на основной ступени; stress до `4 × RATE`    |
| `PRE_ALLOCATED_VUS` | `20`                    | Заранее выделенные VU                                     |
| `MAX_VUS`           | `100`                   | Максимум VU, не меньше PRE_ALLOCATED_VUS                  |
| `P95_MS`            | `500`                   | Порог p95 в миллисекундах                                 |
| `P99_MS`            | `1000`                  | Порог p99 в миллисекундах                                 |

Пороги — начальные бюджеты, а не обещание производительности: p95 < 500 мс,
p99 < 1000 мс, HTTP failures < 1%, ноль невалидных ответов и 100% успешных checks.
Таким образом любая HTTP/GraphQL/структурная ошибка делает прогон неуспешным.
Нулевая `dropped_iterations` в load/stress не позволяет считать успешным тест,
в котором генератор не выдержал заданную интенсивность. В таком случае проверьте
ресурсы генератора и число VU, прежде чем делать выводы о сервере.

Предварительный запрос в `setup` проверяет наличие профиля и немедленно останавливает
тест при ошибке. Для latency используются метрики запросов `GetProfile`, включая
этот запрос. Timeout каждого запроса — 10 секунд. Нагрузка задаётся arrival rate,
без `sleep`, и не уменьшается автоматически при замедлении сервера.

Это API-тест: он не измеряет рендер React, Web Vitals и загрузку ассетов.
Для воспроизводимых измерений запускайте production build на отдельном стенде,
фиксируйте размер данных, ресурсы API/PostgreSQL и версию приложения. Генератор
желательно запускать отдельно от сервера. Smoke подтверждает работоспособность
сценария, но не доказывает, что сервер выдерживает нагрузку.

## Проверка самих сценариев

```sh
npm run test:load:unit
npm run test:load:integration
```

Unit-тесты проверяют конфигурацию и отклонение некорректных ответов, включая HTTP 200
с GraphQL errors. Интеграционный smoke поднимает настоящую отдельную PostgreSQL
через существующий Testcontainers runner, применяет миграции и запускает Nest API
на случайном порту. k6 сначала должен упасть без профиля, затем пройти с fixture.
Контейнер удаляется runner в `finally`. `TEST_DATABASE_URL` вручную не задавать.
Для этой команды нужны Docker и k6. Длительные load/stress запускаются отдельно от
`verify`, чтобы показатели не зависели от параллельных сборок и coverage.

## Поиск максимума на production

```sh
BASE_URL=https://daniil-ivanov.dev npm run test:load:maximum
```

`maximum.ts` повышает интенсивность по ступеням 10, 25, 50, 100, 200, 400,
800 запросов/с: 15 секунд разгона и 45 секунд удержания на каждой ступени.
Предел генератора — 600 VU. Увеличение останавливается при общем p95 ≥ 2 с
или общей доле невалидных ответов ≥ 5%; оценка начинается после первых 30 с.
Это накопительные пороги k6 за весь прогон, а не скользящее окно. Нормальный
бюджет p95 500 мс нужно отдельно оценивать на каждой ступени по сырым данным.
Пропущенные итерации делают итог неуспешным и могут означать ограничение генератора.
Если все ступени пройдены, установлен только нижний предел мощности, не максимум.
Один внешний генератор измеряет весь путь до API, включая сеть, TLS и прокси;
без серверных метрик причина насыщения не устанавливается.

Для сохранения данных и графиков:

```sh
mkdir -p artifacts/k6-capacity
BASE_URL=https://daniil-ivanov.dev k6 run \
  --out json=artifacts/k6-capacity/raw.json.gz \
  --summary-export=artifacts/k6-capacity/summary.json load/maximum.ts
```
