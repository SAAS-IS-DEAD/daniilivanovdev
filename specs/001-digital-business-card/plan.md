# Implementation Plan: воркер hh.ru вместо админки

**Branch**: `001-digital-business-card` · **Updated**: 2026-11-04
**Spec**: [spec.md](spec.md)

## Сохраняем

TypeScript + Node.js + NestJS, PostgreSQL + Prisma, GraphQL + Apollo Sandbox,
React/Vite и GraphQL Code Generator + graphql-request SDK. API обслуживает только
чтение. Интерактивная визитка и существующие seed-данные продолжают работать.

## Архитектура синхронизации

Отдельный entrypoint Nest application context в том же кодовом проекте и отдельный
Compose service `worker` без HTTP-порта. Использует ту же Prisma-модель и прикладные
правила, но не вызывает публичные mutations. Redis/очередь для одного резюме не нужны.

`source adapter → parser/mapper → validated snapshot → sync service → repository → Prisma`.
Сетевой адаптер не пишет в БД; parser не делает сетевых запросов. В транзакции
используется блокировка на источник, чтобы повторный процесс не применял снимок параллельно.
Сетевой запрос выполняется с конечным таймаутом и лимитом размера ответа; источник
задаётся оператором с фиксированным HTTPS host/path, без произвольного URL от посетителя.

## Владение данными

Предварительный mapping, проверяется на реальном снимке до включения синхронизации:
имя → name; желаемая должность → specialization; «О себе» → description;
навыки → skills; места работы → experience. Отсутствующее поле не означает очистку.
Явно пустой список принимается только при подтверждённо полном снимке.
Проекты, ProfileLink и контакты из локального контента сохраняются. Поскольку сейчас
контакты включены в description, до первого импорта выделить локальный блок и собирать
итоговое описание из импортируемого текста и сохранённых локальных дополнений.

Связи получают provenance (source/sourceKey); существующие локальные записи нельзя
массово удалять. Первая синхронизация сначала строит dry-run diff и сопоставляет
совпадающие записи; неоднозначные совпадения не применяются автоматически.
Существующий source ID используется как ключ; если источник его не даёт, правило
сопоставления фиксируется отдельно после изучения примера. Идентификаторы сохраняются.
Удалять можно только hh-managed записи, отсутствующие в полном валидном снимке.

## Расписание и отказы

Включение флагом, по умолчанию off. Включённый worker — при старте и раз в сутки;
CLI `sync --once --dry-run` / `sync --once` планируется для оператора.
403/404/капча/schema mismatch не вызывают немедленных повторов. 429 учитывает Retry-After;
сеть/5xx — ограниченные повторы с backoff. После исчерпания — последняя версия в БД.
Readiness сайта не зависит от hh.ru; состояние источника доступно оператору в логах/CLI.
Логи содержат статус, время, количества, но не HTML, контакты или токены.

## Проверки и rollout

Fixture тесты парсинга только по подтверждённой структуре; локальные HTTP mocks для
200/403/429/таймаута/частичного ответа; отдельная БД для атомарности, идемпотентности,
конкурентного запуска и сохранения локальных полей. Тесты CI не обращаются к hh.ru.
Сначала dry-run на реальном ответе и backup, затем первый импорт и повторный прогон.
Только после этого включить расписание. Проверить Docker без сети и restart.

## Удалённый объём

## Quality gate — 2026-11-05

Для каждой фичи обязательны unit-тесты, для backend дополнительно интеграционные.
`npm run verify` и `.github/workflows/ci.yml` выполняют проверки с coverage thresholds.
Матрица и точные границы измерения: docs/testing.md. Воркер hh.ru остаётся на паузе.

## Testcontainers — 2026-11-05

Интеграционные тесты и coverage запускаются через Node runner с
@testcontainers/postgresql. Каждый прогон получает PostgreSQL 17.6, динамический
порт и случайное имя базы/пароль. Миграции выполняются до тестов, очистка — в finally;
Ryuk включён. Постоянная compose.test.yaml больше не используется и удалена.
Нужен работающий Docker; CI выполняет npm run verify без ручного старта PostgreSQL.

## Deployment ownership (2026-11-06)

Deployment is owned exclusively by SAAS-IS-DEAD/infra. Application CI validates
application code and publishes the release image. Argo and Image Updater track
infra/deploy/k3s-02; application-repository deployment paths are historical only.
